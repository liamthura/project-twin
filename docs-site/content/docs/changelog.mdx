Versions here are the app version, shown at the foot of Settings → Account as
`v2.3.0 (a1b2c3d)` with the commit it was built from. Releases before 2.1.0
predate this page.

## 2.3.0

Review is safer to work through quickly: an update shows what it would
replace, and Approve can be undone. The rest is fixes from a design review of
the web app. No migration and no new setting.

### Review

- **Updates say what they replace.** A row reads "Notes: Paused for now →
  Weekly tutor", and so do its details and the edit form, so the value on
  record is in front of you before you overwrite it. An update that would
  change nothing says so.
- **Approve has an Undo.** Approve, `a` and bulk Approve now wait for their
  confirmation, as Reject and Delete already did, and the confirmation links
  to the section the change went into. Leaving Review sends anything still
  waiting.
- **Undo means undo.** A decision is sent when its confirmation goes, and the
  confirmation stays while the pointer or focus is on it. Before, a decision
  went out after eight seconds even while its toast still offered Undo, and a
  toast that closed under the pointer could leave the next one standing.
- **Observations** use the Inbox row's layout, with the section named as the
  editor names it.
- **Contrast and layout.** Approve's green passes WCAG AA as text, and Approve
  and Reject sit in the same place on every row.
- **Why?** now works on entries changed through Review, not only ones added
  through it, for changes approved from this version on.

### Elsewhere

- Dates read "28 July 2026", with the time after a comma where there is one,
  everywhere the editor shows them. An opened entry no longer repeats a date
  its row shows in full.
- Search results are grouped by section for screen readers, and a match deep
  in a long field shows in the snippet.
- A dialog's close button is a 44px target on touch screens, and dialog titles
  sit on the left on a phone too.
- **Help and docs** in the account menu, a filter without a second "Clear",
  and 44px list rows on touch screens.

### Upgrading

Pull the image and restart. Nothing else is needed.

## 2.2.0

A security fix for password sign-in, the app moving to `/app/`, and a rebuilt
web app: Review, History, search, and a record of where every entry came from.
Assistants get a clearer contract and five new entry types. One database
migration, which applies itself on start.

<Callout type="warn">
Upgrade promptly. In 2.1.0 and earlier, a write-scoped token (the kind that
sits in an `.mcp.json`) could set an account's password without the current
one, because the check read a column that accounts created through sign-up
never fill. It now checks the password sign-in actually uses, and an account
with no password can be given one only from a signed-in browser, never with a
token. The old login route also stops accepting a password that a reset has
replaced.
</Callout>

### The app lives at `/app/`

`/` is the landing page, and the app, its sign-in and its consent screens are
under `/app/`. The old sign-in and consent paths redirect there with the query
intact, so an authorisation already under way still finishes. Bookmarks such
as `/#/profile` and links in emails sent before the move are forwarded from
the browser. Anything that launches the app at the root, such as an identity
provider's launch URL, should now point at `/app/`.

### Sign-in rate limits

The auth container now runs in production mode, which is what switches Better
Auth's rate limits on: sign-in, and the OAuth register, token and authorize
routes, were all unlimited before. The limits count per visitor, so behind a
reverse proxy set `FORWARDED_ALLOW_IPS`, and behind a CDN
`AUTH_CLIENT_IP_HEADER` and `AUTH_CLIENT_IP_HEADER_FROM` as well. Without them
every visitor looks like the proxy and shares one allowance of 3 sign-in
requests per 10 seconds. See [Self-hosting](/run/self-hosting).

### Review

- **Edit before approving.** Open a suggestion to correct it, then approve
  your version.
- **Undo.** Reject and Delete wait 8 seconds with an Undo before they reach the
  server.
- **Several at once.** Tick rows, or Select all, to approve, reject or delete
  them together. Rejecting several has one Undo.
- **Keyboard.** On a focused row, `j` and `k` move, `a` approves, `r` rejects,
  `e` edits and `x` selects. `?` lists them.
- **Each row** says where the change goes, why the assistant suggested it, and
  the words of yours it quoted.

### Where entries came from, and stale entries

Open an entry to see who added it and who last changed it, and when: you, an
app writing directly, or a suggestion approved in Review. For those, **Why?**
shows the reasoning and the quote. This is recorded from 2.2.0 on; older
entries show when they last changed.

Goals and Projects are marked stale after four months unchanged, and
Knowledge after a year. **Keep** restarts an entry's clock without changing
it. A list's header counts its stale entries and filters to them, and Review
has a **Stale** tab across every section. The `stale` flag assistants see now
counts from the later of the last change and the last Keep.

### History and search

**Restore this** first shows what restoring a version would bring back, remove
and change, compared with now. Search, from the header or ⌘K (Ctrl+K), finds
words in every section and opens a result at its entry. On an instance with an
embeddings provider it adds entries related by meaning.

### For assistants

- `propose_update`'s description lists every entry type with its required
  fields. Most suggestions that arrived as observations had a type the client
  never looked up.
- Preferences' Learning Style and Code Style lists are typed:
  `learning_method`, `learning_dislike`, `preferred_language`, `framework` and
  `dev_tool`, each `item`-identified and add or remove. `get_schema` returns 49
  entities. The existing 44 are unchanged, and a client written against 2.1.0
  keeps working.
- Tokens created in the app propose by default. Writing directly is a switch
  you turn on when creating one.

### New web API routes

`GET /api/provenance/{section}`, `GET /api/stale`,
`POST /api/provenance/{entity_id}/keep`, `GET /api/history/{section}/{id}` and
`GET /api/search?q=`. All are REST-only, like History: assistants reach none of
them.

### Upgrading

Pull the image and restart. Migration `0011_persona_provenance` adds one table
and runs on start with the rest (`alembic upgrade head` is the image's first
step). There is no new required setting; behind a proxy, set the variables
under [Sign-in rate limits](#sign-in-rate-limits).

## 2.1.0

The write path an AI client uses is now one implementation driven by the
section packs, rather than one hand-written block per entity. Most of what
follows is the consistency that came with it.

### Write confirmations

Every write answers in the same shape, whichever entity it touched:

```
✅ Added trait: Curious
ℹ️ Trait 'Curious' already exists
❌ Trait 'Curious' not found
✅ Added spec 'RAM' to thuradev-main
❌ Goal requires 'title'
```

Before, each entity phrased its own, so adding a club said `ℹ️ 'Chess' already
in clubs` where adding a connection said `ℹ️ Connection 'Chess' already
exists`. 137 of the 235 recorded write results changed wording. Nothing about
which writes succeed changed with them.

### Duplicate rows

Adding a reference, a coursework entry or a work experience that already
exists is refused with `ℹ️ ... already exists`. Four entities used to append a
second copy of it, which left a row you could see twice and remove once.

### Row timestamps

Editing a row's children now touches that row's `last_updated`, so a hobby
whose references changed reads as touched today. Search results report their
age from this date, and three of the five child entities were not updating it.

### List matching

A list of plain strings matches case-insensitively when you add to it, which
is how removing from one already worked. `Tight deadlines` alongside `tight
deadlines` left one of the pair unremovable.

### New rows

A new row carries every field its section declares, empty, instead of only the
fields you sent. The editor drew them as empty either way; now the stored JSON
says so too.

### Custom enum labels

A field that accepts a value outside its list keeps yours under
`custom_<field>`, and says so in the confirmation:
`✅ Added goal: Serve community (type 'volunteering' stored as
other/custom_type)`. You can also correct the label on its own, without
re-sending the value it belongs to.

### References taking their parent's name

Fixed: a reference sent as `{"domain_name": "Rust", "title": "The Book"}` was
stored named "Rust", the domain's name rather than the reference's, and one
sent with the parent selector alone created a reference named after the domain
it sat under. `title`, `reference_name` and `reference` are documented
spellings for a reference's own name and now resolve to it. Rows already
written this way keep the wrong name until you rename them.

### Section packs

A nested element works from a manifest alone. `derive_write_targets` records
where its rows live and the write path reads that, so `add`, `update` and
`remove` on a child row need no Python. This was the one shape a contributed
pack could not ship; [Section packs](/run/section-packs) covers what a
manifest now has to say.

The published entity contract is unchanged. `get_schema` returns the same 44
entities with the same fields, and a client written against 2.0.0 keeps
working.

### Upgrading

Pull the image and restart. There is no schema migration and no new
environment variable, and existing rows are left as they are.

<Callout type="warn">
The one-shot data migrations are gone from this release: `migrate_json_to_postgres`,
`migrate_goals` and `migrate_consolidation`. They each ran once against a
database that predates Postgres storage, the goals section, or the interests
consolidation. If yours has not had all three, run them from an earlier tag
before upgrading.
</Callout>
