Versions here are the app version, shown at the foot of Settings → Account as
`v0.4.3 (a1b2c3d)` with the commit it was built from. Releases before 0.2.1
predate this page.

MyGist is pre-1.0, and its versions say so. Until 0.2.4 they were numbered one
place higher, so 0.2.3 was released as 2.3.0, 0.2.2 as 2.2.0, 0.2.1 as 2.1.0,
0.2.0 as 2.0.0 and 0.1.0 as 1.0.0. Nothing else about those releases changed.

## Unreleased

The editor loads a section the first time you open it, instead of your whole
persona when the page opens. On a persona with about 190 entries, the persona
data fetched on opening went from 143,000 characters to Profile's 8,000.
Sections you have opened stay in the page until you sign out.

- Nothing from your persona is kept outside the page: API responses are sent
  with `Cache-Control: no-store`, so the browser does not keep a copy in its
  cache, and signing out clears what the page held.
- Search covers sections you have not opened through the server's index. Until
  a section is opened, it matches that section's entries but not standalone
  fields such as your bio.
- An update waiting in Review loads the section it would change, so it still
  shows what it replaces.

### Upgrading

Pull the image and restart. No migration.

## 0.4.3

Connected AI clients read less of your persona at once, and none of it is
lost. Every scope except `minimal` returns an index of titles, and the client
fetches the entries it needs. On a persona with about 190 entries, `full` went
from 148,000 characters to 22,000. See [Reading](/use/reading).

- Apart from `get_raw`, the export, no read returns more than 32,000
  characters, about 8,000 tokens. Anything
  shortened to fit is listed under `trimmed`, with the call that reaches it.
- Every scope that includes the learning log returns its newest 10 entries;
  `learning` keeps its 60-day window.
- Index entries carry `status`, so a client can tell active work from finished
  work without fetching it.
- Every tool says whether it only reads. ChatGPT and Claude can run the read
  tools without asking each time. `persona_modify` and `persona_batch` are
  marked destructive, because they can remove entries, so Claude always asks
  before those.
- Errors come back flagged as errors, rather than as text starting with ❌.
- Entries and sections can be opened as MCP resources, `mygist://entity/{id}`
  and `mygist://section/{key}`, with the same `persona:read` permission as the
  tools.
- Every tool description fits in 2,048 characters, where Claude Code cuts them
  off.

### Upgrading

Pull the image and restart. No migration. A client that parsed `get_context`
output expecting full entries should pass `detail="full"`.

## 0.4.2

Emails look like MyGist. Password reset, email confirmation, approving an email
change and the invite arrive as a short designed email, with dark-mode colours
for mail apps that use them and a plain-text version alongside. Their copy is rewritten,
and each says how long its link works.

- Their wording can change without a deploy, with `python scripts/emails.py`.
  See [Email](/run/self-hosting#email).
- The editor tour (Show me around) ends on the Feedback button.

### Upgrading

One migration, `0013_email_copy`, which runs on start. Nothing to set: with no
edits, every email uses its default wording.

## 0.4.1

Signing out lands on the sign-in page. It showed Couldn't reach MyGist
instead: the app still thought you were signed in, so it read the refused
reload that follows signing out as the server being down.

### Upgrading

Pull the image and restart. No migration.

## 0.4.0

A Feedback button in the bottom right of every signed-in screen opens a short
form for a problem, an idea or anything else, with a screenshot you attach or
paste. Error messages have a Report button that opens it with the error filled
in.

- A report carries your username, the page, the version, and your browser and
  screen size, never your persona. A screenshot is shrunk in your browser,
  which drops a photo's location.
- Reports are saved, emailed to whoever runs the instance, and deleted with
  the account. An account can send 10 an hour.
- Sign in opens on username and password. Where an instance has a sign-in
  provider, its button sits under the form rather than in front of it.

### Upgrading

One migration, `0012_feedback`, which runs on start. To have reports emailed,
set `FEEDBACK_TO` on the API with `RESEND_API_KEY` and `EMAIL_FROM`. Without
them, reports are saved and `python scripts/feedback.py` lists them.

## 0.3.0

A new first run that ends on your first approved suggestion. After signing up
you choose the assistant you use, follow its own steps, and paste a prompt; the
screen follows the assistant as it connects, reads your persona and suggests
things, then takes you to Review for the first one. Typing it yourself ends
with a short tour of the editor instead.

- Connect is three screens: which assistant, its steps, and who fills it in.
  Something else holds the paste-in prompt and the token, and a token keeps
  its steps beside it. An existing token no longer hides the sign-in steps.
- Connected now means the assistant has called, everywhere it is shown. The
  Getting started card ticks only what happened, its third step can be
  ticked, and Show getting started brings it back as it was.
- Guides, shown once per account and remembered on the server: your first
  suggestion in Review, a tour of the editor (Show me around in the account
  menu replays it), and hints on Promote, your first connected app, and where
  to paste the prompt. The confetti moved to your first approval.
- The Claude entry covers claude.ai and the desktop app, with Claude's current
  steps (Customize → Connectors).
- About you shows when it has saved, leaves nationality to Profile, and starts
  the locale from your browser's language.

### Upgrading

Pull the image and restart. No migration. `/api/usage` is now
`/api/watchtower`, which returns the same `activity` rows plus `connection`,
`assistant` and `pending`; the old name still answers in 0.3.x and goes in the
next minor release.

## 0.2.5

Suggestions are written in your voice. What an assistant proposes becomes your
persona, so it now reads as you would put it yourself: "I batch cook on
Sundays for the week", not "Batch cooks on Sundays". Names and titles stay
names, and the reason under a suggestion is still the assistant talking to
you: "You mentioned the routine twice." No migration and no new setting.

- The `propose_update` tool description and the MyGist skills ask for it,
  with their examples rewritten in the new voice. Direct writes follow the
  same rule, so a persona does not end up in two voices.
- Suggestions already in your queue keep the words they were sent with.

### Upgrading

Pull the image and restart. An assistant picks the change up when it next
fetches its tool list; one that caches it may need restarting.

## 0.2.4

Review keeps each decision's Undo, and can suggest where an observation
belongs. You can delete your account. The rest is fixes from a second design
review of the web app. No migration; one optional setting.

### Review

- **Confirmations stack.** Approving the next row no longer sends the last one
  with no way back: each decision keeps its Undo until its own confirmation
  goes. Hover the stack, or Tab into it, to spread it out and stop every
  clock. Decisions are still sent one at a time.
- **Confirmations name the entry**, as "Hana added to Circle", count a bulk
  approval by what each did ("Approved 4: 2 added, 2 updated"), and show their
  eight seconds running out.
- **Promote uses the editor's names** for types, says what the chosen type is
  for, and no longer picks the first type for you.
- **Promote shows the type's fields**, and takes any type a section shows,
  such as a job, waiting for the required fields.
- **Suggestions**, on an instance with a TypeSafe key: Promote offers the
  three likeliest places for an observation, from any section, chooses the
  type when the suggestion is sure, and fills its fields from the
  observation's own words, with the sentence in its notes. Edit before
  approving offers to tidy a suggested entry whose name is a whole sentence.
  See [Suggestions in Review](/run/self-hosting#suggestions-in-review).
- `?`, `j` and `k` work before a row has been clicked.

### Your account

- **Delete account**, at the foot of Settings → Account, removes your persona,
  its history, your suggestions, tokens and connected apps. It offers a
  download first, asks you to type your username, and works only from a
  browser sign-in: no assistant can delete your account.

### Elsewhere

- A list's filters sit behind one icon at the end of its search box, tinted
  while one is on.
- Search marks the word that matched and cuts snippets at whole words.
- Token and History dates read like every other date; a token no client has
  used says "not used yet".
- Every status is the same control, taste chips (loved, dislike) lose their
  colour, titles wrap on a phone, and an opened entry no longer repeats a
  field its own box shows.
- Section headings are in sentence case, Circle adds a "person", and Add
  dialogs no longer repeat their heading.

### For pack authors

- `about` on an element or variant says what one entry means to a person:
  `what`, `not_for` and `examples`. The Promote dialog shows it, and
  suggestions route on it. See [`about`](/run/pack-reference#about).
- `noun` names one entry on screen ("Add person").

### Upgrading

Pull the image and restart. To turn suggestions on, set `TYPESAFE_API_KEY`;
observations' notes, reasons and quotes are then sent to TypeSafe when Promote
opens, and a suggested entry's name and quote when you edit one to tidy.

## 0.2.3

Review is safer to work through quickly: an update shows what it would
replace, and Approve can be undone. The rest is fixes from a design review of
the web app. No migration and no new setting.

### Review

- **Updates say what they replace.** A row reads "Notes: Paused for now →
  Weekly tutor", and so do its details and the edit form, so the value on
  record is in front of you before you overwrite it. An update that would
  change nothing says so.
- **Approve has an Undo.** Approve, `a` and bulk Approve now wait for their
  confirmation, as Reject and Delete already did, and the confirmation links
  to the section the change went into. Leaving Review sends anything still
  waiting.
- **Undo means undo.** A decision is sent when its confirmation goes, and the
  confirmation stays while the pointer or focus is on it. Before, a decision
  went out after eight seconds even while its toast still offered Undo, and a
  toast that closed under the pointer could leave the next one standing.
- **Observations** use the Inbox row's layout, with the section named as the
  editor names it.
- **Contrast and layout.** Approve's green passes WCAG AA as text, and Approve
  and Reject sit in the same place on every row.
- **Why?** now works on entries changed through Review, not only ones added
  through it, for changes approved from this version on.

### Elsewhere

- Dates read "28 July 2026", with the time after a comma where there is one,
  everywhere the editor shows them. An opened entry no longer repeats a date
  its row shows in full.
- Search results are grouped by section for screen readers, and a match deep
  in a long field shows in the snippet.
- A dialog's close button is a 44px target on touch screens, and dialog titles
  sit on the left on a phone too.
- **Help and docs** in the account menu, a filter without a second "Clear",
  and 44px list rows on touch screens.

### Upgrading

Pull the image and restart. Nothing else is needed.

## 0.2.2

A security fix for password sign-in, the app moving to `/app/`, and a rebuilt
web app: Review, History, search, and a record of where every entry came from.
Assistants get a clearer contract and five new entry types. One database
migration, which applies itself on start.

<Callout type="warn">
Upgrade promptly. In 0.2.1 and earlier, a write-scoped token (the kind that
sits in an `.mcp.json`) could set an account's password without the current
one, because the check read a column that accounts created through sign-up
never fill. It now checks the password sign-in actually uses, and an account
with no password can be given one only from a signed-in browser, never with a
token. The old login route also stops accepting a password that a reset has
replaced.
</Callout>

### The app lives at `/app/`

`/` is the landing page, and the app, its sign-in and its consent screens are
under `/app/`. The old sign-in and consent paths redirect there with the query
intact, so an authorisation already under way still finishes. Bookmarks such
as `/#/profile` and links in emails sent before the move are forwarded from
the browser. Anything that launches the app at the root, such as an identity
provider's launch URL, should now point at `/app/`.

### Sign-in rate limits

The auth container now runs in production mode, which is what switches Better
Auth's rate limits on: sign-in, and the OAuth register, token and authorize
routes, were all unlimited before. The limits count per visitor, so behind a
reverse proxy set `FORWARDED_ALLOW_IPS`, and behind a CDN
`AUTH_CLIENT_IP_HEADER` and `AUTH_CLIENT_IP_HEADER_FROM` as well. Without them
every visitor looks like the proxy and shares one allowance of 3 sign-in
requests per 10 seconds. See [Self-hosting](/run/self-hosting).

### Review

- **Edit before approving.** Open a suggestion to correct it, then approve
  your version.
- **Undo.** Reject and Delete wait 8 seconds with an Undo before they reach the
  server.
- **Several at once.** Tick rows, or Select all, to approve, reject or delete
  them together. Rejecting several has one Undo.
- **Keyboard.** On a focused row, `j` and `k` move, `a` approves, `r` rejects,
  `e` edits and `x` selects. `?` lists them.
- **Each row** says where the change goes, why the assistant suggested it, and
  the words of yours it quoted.

### Where entries came from, and stale entries

Open an entry to see who added it and who last changed it, and when: you, an
app writing directly, or a suggestion approved in Review. For those, **Why?**
shows the reasoning and the quote. This is recorded from 0.2.2 on; older
entries show when they last changed.

Goals and Projects are marked stale after four months unchanged, and
Knowledge after a year. **Keep** restarts an entry's clock without changing
it. A list's header counts its stale entries and filters to them, and Review
has a **Stale** tab across every section. The `stale` flag assistants see now
counts from the later of the last change and the last Keep.

### History and search

**Restore this** first shows what restoring a version would bring back, remove
and change, compared with now. Search, from the header or ⌘K (Ctrl+K), finds
words in every section and opens a result at its entry. On an instance with an
embeddings provider it adds entries related by meaning.

### For assistants

- `propose_update`'s description lists every entry type with its required
  fields. Most suggestions that arrived as observations had a type the client
  never looked up.
- Preferences' Learning Style and Code Style lists are typed:
  `learning_method`, `learning_dislike`, `preferred_language`, `framework` and
  `dev_tool`, each `item`-identified and add or remove. `get_schema` returns 49
  entities. The existing 44 are unchanged, and a client written against 0.2.1
  keeps working.
- Tokens created in the app propose by default. Writing directly is a switch
  you turn on when creating one.

### New web API routes

`GET /api/provenance/{section}`, `GET /api/stale`,
`POST /api/provenance/{entity_id}/keep`, `GET /api/history/{section}/{id}` and
`GET /api/search?q=`. All are REST-only, like History: assistants reach none of
them.

### Upgrading

Pull the image and restart. Migration `0011_persona_provenance` adds one table
and runs on start with the rest (`alembic upgrade head` is the image's first
step). There is no new required setting; behind a proxy, set the variables
under [Sign-in rate limits](#sign-in-rate-limits).

## 0.2.1

The write path an AI client uses is now one implementation driven by the
section packs, rather than one hand-written block per entity. Most of what
follows is the consistency that came with it.

### Write confirmations

Every write answers in the same shape, whichever entity it touched:

```
✅ Added trait: Curious
ℹ️ Trait 'Curious' already exists
❌ Trait 'Curious' not found
✅ Added spec 'RAM' to thuradev-main
❌ Goal requires 'title'
```

Before, each entity phrased its own, so adding a club said `ℹ️ 'Chess' already
in clubs` where adding a connection said `ℹ️ Connection 'Chess' already
exists`. 137 of the 235 recorded write results changed wording. Nothing about
which writes succeed changed with them.

### Duplicate rows

Adding a reference, a coursework entry or a work experience that already
exists is refused with `ℹ️ ... already exists`. Four entities used to append a
second copy of it, which left a row you could see twice and remove once.

### Row timestamps

Editing a row's children now touches that row's `last_updated`, so a hobby
whose references changed reads as touched today. Search results report their
age from this date, and three of the five child entities were not updating it.

### List matching

A list of plain strings matches case-insensitively when you add to it, which
is how removing from one already worked. `Tight deadlines` alongside `tight
deadlines` left one of the pair unremovable.

### New rows

A new row carries every field its section declares, empty, instead of only the
fields you sent. The editor drew them as empty either way; now the stored JSON
says so too.

### Custom enum labels

A field that accepts a value outside its list keeps yours under
`custom_<field>`, and says so in the confirmation:
`✅ Added goal: Serve community (type 'volunteering' stored as
other/custom_type)`. You can also correct the label on its own, without
re-sending the value it belongs to.

### References taking their parent's name

Fixed: a reference sent as `{"domain_name": "Rust", "title": "The Book"}` was
stored named "Rust", the domain's name rather than the reference's, and one
sent with the parent selector alone created a reference named after the domain
it sat under. `title`, `reference_name` and `reference` are documented
spellings for a reference's own name and now resolve to it. Rows already
written this way keep the wrong name until you rename them.

### Section packs

A nested element works from a manifest alone. `derive_write_targets` records
where its rows live and the write path reads that, so `add`, `update` and
`remove` on a child row need no Python. This was the one shape a contributed
pack could not ship; [Section packs](/run/section-packs) covers what a
manifest now has to say.

The published entity contract is unchanged. `get_schema` returns the same 44
entities with the same fields, and a client written against 0.2.0 keeps
working.

### Upgrading

Pull the image and restart. There is no schema migration and no new
environment variable, and existing rows are left as they are.

<Callout type="warn">
The one-shot data migrations are gone from this release: `migrate_json_to_postgres`,
`migrate_goals` and `migrate_consolidation`. They each ran once against a
database that predates Postgres storage, the goals section, or the interests
consolidation. If yours has not had all three, run them from an earlier tag
before upgrading.
</Callout>
