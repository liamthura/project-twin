There are two ways to get context out of MyGist, and the difference matters at
scale: **load a scope**, or **search and fetch**. A well-behaved client does the
first once at the start of a conversation and the second every time afterwards.

## Scoped context

`get_context` returns a slice of your persona rather than all of it. Each scope
is assembled from what every section pack declares it contributes.

| Scope | Roughly | Includes |
|---|---|---|
| `minimal` | ~150 tokens | Name, bio, location, current role, top of mind, first few active goal titles |
| `professional` | ~3,600 | Work, skills, projects, domains, active goals |
| `personal` | ~1,400 | Hobbies, values, personality, wellness, active goals |
| `learning` | ~3,400 | Domains, current learning, active goals |
| `full` | ~8,000 | Everything enabled |

Token figures are indicative and drift as your persona grows — treat them as
relative sizes, not budgets.

**Any section key is also a scope**, alone or in a list:

```text
get_context(scope="lifestyle")
get_context(scope=["lifestyle", "circle"])
```

### Narrowing further

**Topic filtering** keeps only entries relevant to a subject, routed through the
search index — semantic matching where embeddings are configured, ranked keyword
matching otherwise:

```text
get_context(scope="professional", topic="Python")
```

**Titles mode** replaces every list entry with an `{id, title, updated_at}` stub:

```text
get_context(scope="professional", detail="titles")
```

On a real persona that took a professional scope from ~7,100 tokens to ~1,600.
Skim the stubs, then fetch the handful that matter. `updated_at` is there so a
client can discount stale context; top-of-mind entries untouched for more than
30 days add a one-line staleness note to the output.

## Search and fetch

This is the pattern the tools are designed around:

```text
search_context("postgres")   → ~10 ranked snippets, each with an entity id
get_entity(["proj_a1b2c3"])  → full detail, only for the hits worth having
```

`search_context` is hybrid where an embedding provider is configured — full-text
*and* vector similarity, so paraphrases match — and full-text only otherwise.
It accepts `sections` to narrow, `limit` (max 25), and `days` for a recency
window.

`get_entity` takes one id or up to 25. Pass `include_related=true` to get an
entry's explicit links and its derived semantic neighbours.

<Callout>
Prefer this over widening a scope. Pulling a whole section to answer one question
costs tokens on every turn afterwards; two small calls cost them once.
</Callout>

## Raw access

`get_raw` dumps whole persona files verbatim. It is for export and debugging, not
for conversation — it bypasses every scope and returns storage keys rather than
the entity vocabulary.

## Asking in practice

You do not call any of this yourself. You ask, and the client chooses:

> What do you know about me?
> What am I currently working on?
> What did I decide about the database last month?

The last one is the interesting case: it is a search, not a scope, and a client
that reaches for `search_context` will answer it from your learning log without
loading anything else.
