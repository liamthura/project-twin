There are two ways to get context out of MyGist:

1. **Load a scope**, a pre-shaped slice of your persona.
2. **Search, then fetch**: find the handful of entries that matter, and pull
   only those.

A well-behaved client does the first once at the start of a conversation, and
the second every time after that. The difference matters more the bigger your
persona gets.

## Scopes

`get_context` returns a slice of your persona. There are five global scopes:

| Scope | What it is for |
|---|---|
| `minimal` | A quick "who is this": name, bio, location, role, top of mind, a few goal titles |
| `professional` | Work context: jobs, skills, projects, domains, active goals |
| `personal` | Hobbies, values, personality, wellness, active goals |
| `learning` | Domains, current learning, the learning log, active goals |
| `full` | Everything that is enabled |

Every scope except `minimal` returns an index: each entry as
`{id, title, status, updated_at}`, with your preferences and the other fields
that are not lists in full. The client reads the index and fetches the entries
that matter by id. `minimal` comes back in full, because it is small and it is
the read a client makes at the start of a conversation.

On a persona with about 190 entries, this took `full` from 148,000 characters
to 22,000, and `professional` from about 30,000 to 9,900.

### Which sections each scope pulls from

| | minimal | professional | personal | learning |
|---|:--:|:--:|:--:|:--:|
| Profile | ● | ● | ● | ● |
| Goals | ● | ● | ● | ● |
| Preferences | ● | ● | ● | ● |
| Knowledge | | ● | ● | ● |
| Projects | ● | ● | | ● |
| Lifestyle | | | ● | |
| Circle | | | ● | |
| Learning log | | | | ● |
| Media *(opt-in)* | | | ● | |
| Aesthetics *(opt-in)* | ● | | ● | |

Preferences appear in every row on purpose. However narrow the request, a client
still learns how you want answers written.

`full` includes every enabled section. A section you have disabled appears in
nothing.

### Reading one section

Any section name is also a scope, on its own or in a list:

```text
get_context(scope="lifestyle")
get_context(scope=["lifestyle", "circle"])
```

## Narrowing further

These change how much of a scope comes back, without changing which sections
it covers.

### Filter by topic

```text
get_context(scope="professional", topic="Python")
```

Only entries relevant to the topic survive. This routes through the search
index: semantic matching where embeddings are configured, ranked keyword
matching otherwise.

### Full detail

```text
get_context(scope="professional", detail="full")
```

Every entry in full, as `minimal` returns them. A client asks for this when a
task needs all of a section, such as writing your CV. `detail="titles"` does the
reverse for `minimal`.

Entries carry `updated_at` in both modes, so a client can discount stale
context. Top-of-mind entries untouched for over 30 days add a one-line
staleness note to the output.

### The learning log

The learning log only grows, so every scope that includes it returns the newest
10 entries. `learning` returns the last 60 days instead. `days` and `limit`
change either:

```text
get_context(scope="learning_log", days=30)
get_context(scope="learning_log", limit=25)
```

## Search and fetch

This is the pattern the tools were designed around:

```text
search_context("postgres")   → about ten ranked snippets, each with an entity id
get_entity(["proj_a1b2c3"])  → full detail, for only the hits worth having
```

**`search_context`** is hybrid where an embedding provider is configured:
full-text *and* vector similarity, so paraphrases match. Without one it is
full-text only, and needs a shared keyword to hit. It accepts:

| Option | Does |
|---|---|
| `sections` | Restrict to certain sections |
| `limit` | Cap the results, maximum 25 |
| `days` | Only entries changed in the last N days |

**`get_entity`** takes one id, or up to 25 at once. Pass
`include_related=true` to also get an entry's links and its derived semantic
neighbours, covered on [Relations](/use/relations).

<Callout>
Prefer this over widening a scope. Pulling a whole extra section to answer one
question costs tokens on every turn afterwards. Two small calls cost them once.
</Callout>

## Size limits

Apart from `get_raw`, no read returns more than 32,000 characters, about 8,000
tokens. That keeps
every result under the 10,000-token point where Claude Code starts warning, and
well under the 25,000 at which it saves a result to a file instead of showing
it.

When a result would be bigger, MyGist shortens the largest lists until it fits:
full entries become titles first, then a list keeps only its newest five, then
only its count. Each cut is listed under `trimmed`, with the call that reaches
the rest:

```json
"trimmed": {
  "learning_log.entries": {
    "shown": 5, "total": 52,
    "more": "get_context(scope=\"learning_log\", days=30) or search_context(query, sections=\"learning_log\")"
  }
}
```

A `get_entity` batch that would pass the limit returns the entries that fit and
marks the rest `"deferred"`, to fetch in another call. A single entry always
comes back whole.

## Resources

Clients that read MCP resources can open the same data by URI:

| URI | Returns |
|---|---|
| `mygist://entity/{id}` | One entry in full, as `get_entity` returns it |
| `mygist://section/{key}` | One section as an index of titles |

`get_context` links each section it left out, and `get_entity` links each
deferred entry. Both need the same `persona:read` permission as the tools, and
each link has a tool call alongside it that does the same thing, so nothing
depends on resource support.

## Raw access

`get_raw` dumps whole section files verbatim. It bypasses every scope and
returns raw storage keys, not the entity vocabulary.

Use it for export, and for debugging when the question is what is stored. Avoid
it in normal conversation, where it is both large and harder to read.

## What this looks like in practice

You never call any of this. You ask, and the client picks:

| You say | The client probably calls |
|---|---|
| "What do you know about me?" | `get_context(scope="minimal")` |
| "Help me update my CV" | `get_context(scope="professional")` |
| "What am I working on?" | `get_context(scope="minimal")` or projects |
| "What did I decide about the database last month?" | `search_context`, then `get_entity` |

No scope answers that last question. A client that reaches for `search_context`
answers it straight out of your learning log, without loading anything else.
