MyGist exposes a standard MCP endpoint at `/mcp`, over plain HTTP. Any client
that can reach a URL can use it. There is nothing Claude-specific in the
server.

Every client needs the same URL, `https://your-instance/mcp` or
`http://127.0.0.1:1120/mcp` locally, and then one of two ways to prove who you
are:

| | |
|---|---|
| **OAuth** | The client connects itself. You sign in, approve a consent screen, and there is nothing to copy anywhere. Use it whenever the client offers it. |
| **A bearer token** | You create it yourself and hand it to the client. For anything that can't open a browser to sign in, see [Connecting with a token](#connecting-with-a-token). |

The short version: OAuth is how an application connects, and a token is how you
script.

## Connecting over OAuth

If a client supports OAuth for remote MCP servers, which is increasingly the
default for newer ones, connecting takes nothing but the URL. The client works
out the
rest for itself.

<Steps>

<Step>

### Point the client at the URL

Give it `https://your-instance/mcp`. No token, no header, nothing else to fill
in.

</Step>

<Step>

### It discovers the server

The first request gets a 401 naming where to find MyGist's metadata. The client
follows that to `/.well-known/oauth-protected-resource`, then to MyGist's
authorization server, and registers itself there automatically, with no client id
to obtain in advance. This step is invisible; it's mentioned here only so the
redirect that follows doesn't look unexplained.

</Step>

<Step>

### Sign in, then consent

A browser opens: to sign in if you aren't already, then to a screen naming the
client and the account it's about to connect:

> **Claude Desktop** wants to connect to **your-username**'s persona

Check that name before approving, especially if more than one account is signed
in on that browser. It's the one check nothing downstream can do for you: no
amount of token validation catches the right client approved against the wrong
account.

</Step>

<Step>

### Choose what to grant

Three lines, each a real permission:

| Shown as | Wire name | Can you say no? |
|---|---|---|
| Read your persona | `persona:read` | No: a connection that can't read has nothing to authorise |
| Suggest changes for your approval | `persona:propose` | Yes, starts checked |
| Change your persona directly | `persona:write` | Yes, starts checked |

Both optional lines start checked, because that's what makes a connection
useful day to day. Uncheck **Change your persona directly** to keep an
assistant proposing edits for you to approve rather than applying them; uncheck
both for a connection that can only read.

There's no prompt later asking for more. MCP has no mechanism for a tool call
to request broader access mid-conversation, so this screen is the only place
the grant gets decided. Narrowing or widening afterwards means reconnecting
from scratch; see [Managing a connection](#managing-a-connection).

</Step>

</Steps>

The client now holds a short-lived access token that it refreshes on its own.
Nothing to copy, nothing to renew.

## What the scopes mean

The same three scopes apply everywhere: OAuth connections, and bearer tokens
created after this feature shipped. They're hierarchical: **write** includes
everything **propose** does, which includes everything **read** does. Granting
the broadest one you need is enough; there's no reason to grant more than one.

- **Read your persona**: the assistant can call `get_context`, `search_context`
  and the other read tools. Always granted; it's the floor every connection
  needs to be useful at all.
- **Suggest changes for your approval**: adds `propose_update`. The assistant
  can draft a change with its reasoning, but nothing reaches your persona until
  you approve it in the web editor.
- **Change your persona directly**: adds `persona_modify` and `persona_batch`.
  The assistant writes immediately, without asking first.

A connection without a scope never sees the matching tool. It is absent from the
tool list, so an assistant limited to reading has no `persona_modify` to reach
for in the first place.

## Managing a connection

Every app connected over OAuth shows up in **Account → Connected apps**, next
to API tokens. Each entry shows the client's name and what it's allowed to do.

Revoking removes it from that list and kills its refresh token immediately, so
it can't ask for a new access token again. But an access token it's already
holding is a signed credential MyGist stops tracking the moment it's issued, so
it keeps working until it expires on its own, up to ten minutes later. That's
worth knowing if you're revoking because something is misusing access right
now rather than as routine cleanup.

There's no way to widen or narrow a grant in place. Reconnecting from the
client goes through consent again, where you can choose differently.

## Connecting with a token

A bearer token remains the right tool for anything that has no browser to open:
a cron job, a CI pipeline, a `curl` command, a client that hasn't implemented
remote MCP authorization yet. None of that is a lesser path; it's the same
credential the server itself has always used, scoped now instead of
all-or-nothing.

Create one in **Account → API tokens**, choosing scopes from the same three
lines shown above, then use it directly:

| | |
|---|---|
| **URL** | `https://your-instance/mcp`, or `http://127.0.0.1:1120/mcp` locally |
| **Auth** | `Authorization: Bearer YOUR_TOKEN` |

Create a separate token per client, so revoking one does not disconnect the
rest. A token, unlike an OAuth connection, does not expire on its own. Revoke it
from the same screen once you're done with it.

<Callout>
An older token with no scopes attached still works exactly as it always has,
with all three scopes. Nothing about this feature narrows a credential you
already have; it only adds the option to mint a narrower one.
</Callout>

The client-specific configs below are the token path, spelled out for
Claude Desktop and Claude Code specifically, and anything else that needs an
`Authorization` header set by hand. If your client offers OAuth, you don't
need any of this; the URL is enough.

## Claude Desktop

Covered step by step in the
[quick start](/use/quick-start#connect-your-ai-client).

## Claude Code

```bash
claude mcp add --transport http mygist https://mygist.thuradev.qzz.io/mcp \
  --header "Authorization: Bearer YOUR_TOKEN"
```

Check it registered:

```bash
claude mcp list
```

## Anything else

Most clients want the same three things under some spelling: a name, the URL,
and a set of headers. In MCP terms this is a **streamable HTTP** server, not a
stdio one, so there is no command to run and no process to launch.

If a client only offers stdio, it can usually still reach an HTTP server through
a bridge such as `mcp-remote`. That is outside what MyGist controls; check the
bridge's own documentation.

<Callout>
Config shapes for remote MCP servers have changed more than once across client
versions, and clients disagree about where headers belong. If a config you found
online does not match what your client expects, trust the client's current
documentation. The URL and the bearer token are the only parts that never
change.
</Callout>

## Checking the connection

When a client shows no tools, work outwards from the server. Each check rules
out one layer.

<Steps>

<Step>

### Is the server up?

```bash
curl -s https://mygist.thuradev.qzz.io/api/health
```

This endpoint is public, with no token needed. A connection error or a DNS failure
means the server or the network, not your config.

</Step>

<Step>

### Does the token work?

```bash
curl -s https://mygist.thuradev.qzz.io/api/auth/whoami \
  -H "Authorization: Bearer YOUR_TOKEN"
```

You should get your user id and username back. A **401** means the token is
wrong, revoked, or not being sent. Check for a trailing space when you pasted
it.

Connected over OAuth instead of a static token? There's nothing to paste into
`curl` here, so check that discovery resolves instead:

```bash
curl -s https://mygist.thuradev.qzz.io/.well-known/oauth-protected-resource
```

A 404 there means the server has no `AUTH_MCP_RESOURCE` configured, which is
worth raising with whoever runs the instance and is not fixable from your end.

</Step>

<Step>

### Both pass, still nothing?

Then it is the client's configuration. Common causes:

- The client was not fully restarted after the config change.
- The config file has a JSON syntax error, so the whole file was ignored.
- The URL is missing `/mcp`, or has a trailing slash that the client adds.
- The client strips custom headers on the transport you chose.

[Troubleshooting](/run/troubleshooting) covers the server-side symptoms in more
detail.

</Step>

</Steps>

## Using more than one client

Nothing special is required. Point them all at the same URL with their own
tokens, and they share one persona. A fact written from Claude Code is
immediately visible in Claude Desktop. There is no sync step, because there is
only one copy.
