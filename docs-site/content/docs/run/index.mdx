This half of the documentation is for whoever runs the server — hosting it,
keeping it healthy, and changing what it can store.

If you only want to *use* MyGist, [Using MyGist](/use) is the other half.

## The whole system

MyGist ships as **two containers** on a single origin: the API, and the auth
service behind it.

The API container serves four things — the web UI, the REST API, the MCP
endpoint and this documentation. The web UI and the docs are static output
built into the image, so there is still no frontend service and no build step
at runtime.

The second container runs [Better Auth](https://better-auth.com) and handles
human sign-in. It is **not** published: the API proxies `/auth/*` to it
internally, so a reverse proxy still sees one upstream and one port. It was one
container until sign-in moved there; if you are reading older material that says
so, this is what changed.

```text
                     one origin
   ┌──────────────────────────────────────────────┐
   │  API container                               │
   │    /          web UI (static)                │
   │    /api       REST API                       │
   │    /mcp       MCP endpoint                   │
   │    /docs      this documentation (static)    │
   │    /auth   ───┐  proxied, not published      │
   └───────────────┼──────────────────────────────┘
                   ▼
   ┌──────────────────────────────────────────────┐
   │  auth container — Better Auth, human sign-in │
   └──────────────────────────────────────────────┘
                          │
                   ┌──────────────┐
                   │   Postgres   │  (+ pgvector, optional)
                   └──────────────┘
```

| Path | What | Auth |
|---|---|---|
| `/` | Web UI — Vite and React, built into the image | Signs in at the client |
| `/api` | REST API | Bearer token |
| `/api/health` | Liveness probe | Public |
| `/mcp` | MCP endpoint | Bearer token |
| `/docs` | This site, statically exported | Public |
| `/api/docs`, `/api/redoc` | Swagger and ReDoc for the REST API | Public |

## What you need

**Postgres, and somewhere to run two containers.** That is the whole
requirement list.

[pgvector](/run/database) is optional — without it, search degrades to
full-text only rather than breaking. An embedding provider is optional on top of
that.

## Design decisions worth knowing up front

A few choices explain most of the behaviour you will meet:

**One image, one origin.** The frontend, the docs, the API and the MCP endpoint
all come out of one build and one deployment. There is no CORS configuration and
no second service to keep in step. The cost is that a broken frontend build
blocks a backend fix, which is why CI builds both.

**Migrations run before the server binds.** The container runs
`alembic upgrade head` first, so a failed migration stops the deploy instead of
leaving a half-migrated database serving traffic.

**An invalid section pack halts startup.** It is not skipped with a warning. The
reasoning is on [Section packs](/run/section-packs#an-invalid-pack-stops-the-server).

**The search index is derived.** `persona_search` can always be rebuilt from
`persona_data`, which makes it the safe thing to drop when it looks wrong.
