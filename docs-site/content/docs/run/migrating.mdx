## From legacy `mygist_data/` JSON

Before personas moved into Postgres they lived as JSON files under
`mygist_data/`. If you have those, import them into an account in one pass:

```bash
cd backend
DATABASE_URL="…" python scripts/migrate_json_to_postgres.py --username you
```

This also backfills stable entity ids, so the imported entries are addressable by
`get_entity` immediately.

The directory is kept in the repository purely as a migration source. Nothing
reads it at runtime.

## Between instances

Use the account dialog's **Data → Export**, then **Import** on the target. That
path needs no database access and carries the whole persona, so it is also the
right answer for "move me to a different server".

After importing, [backfill the search index](/run/search-index) — imported
entries are in `persona_data` but not yet in `persona_search`.

## One-off schema migrations

Two scripts exist for structural changes that already shipped. You only need
them if you are bringing forward a database that predates them:

| Script | What it does |
|---|---|
| `scripts/migrate_goals.py` | Moves goals off the profile lists into the goals section |
| `scripts/migrate_consolidation.py` | Unifies interests, likes/dislikes and learning goals into their consolidated lists |

Both are idempotent. Running one on an already-migrated database does nothing.

## Read-time normalisation

Many smaller shape changes need no script at all: `persona_store._normalize`
coerces legacy shapes as the data is read, and every one of those coercions is
lossless and idempotent. Examples of what it handles silently:

- coursework and clubs stored as bare strings, now objects
- mood overrides split across two different keys
- contact links that were separate `github` / `linkedin` fields
- a boolean `response_format` map, now a list of statements

You do not need to do anything about these. They are listed so that a persona
whose stored JSON does not quite match what the editor shows is not mistaken for
corruption.
