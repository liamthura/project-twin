Everything the repository can specify, it specifies: the image, the migrations,
the ports the process binds. What is left over lives in whatever platform you
deploy on — a build setting, a port mapping, a DNS record — and that is the part
nobody can read out of the code six months later.

This page is about that leftover layer. It is deliberately not tied to one
platform: substitute your own, and the things that go wrong are the same.

<Callout>
None of this is required to run MyGist. [Self-hosting](/run/self-hosting) is the
short path — Postgres, two containers, done. Read this when you are putting a
deployment behind a domain and want to know which settings bite.
</Callout>

## The shape

Most hosted deployments end up in the same four layers, whatever the products
are called:

```text
an edge or proxy      DNS, TLS, and a public hostname
      ↓
a build platform      builds the image on push, runs the container
      ↓
the API container     /   /api   /mcp   /docs   (+ /auth, proxied internally)
      ↓
Postgres              with pgvector, if you want hybrid search
```

The middle two are the ones with settings you cannot commit.

## What the platform has to get right

Four settings, and each has a failure that looks like something else.

| Setting | Value | If it is wrong |
|---|---|---|
| Build context | The **repository root** | The build fails outright, which is the honest case |
| Dockerfile | `./Dockerfile` | As above |
| Container port | **1120** | Every request 502s while the container is perfectly healthy |
| Commit stamp | `APP_COMMIT` or `SOURCE_COMMIT` build arg | You cannot tell what is deployed |

<Callout type="warn">
The container port is **1120**, not 8000 or 8080. Nothing in the repository can
enforce the other end of it: the platform's port mapping lives in a dashboard,
so a proxy still pointing at the wrong port produces a 502 on every request
while the container itself reports healthy. It reads like an application fault
and is not one.
</Callout>

The build context is the repository root because earlier stages build the web UI
and this documentation and copy their output into the final image. Pointing it
at `backend/` builds a different, API-only image.

`APP_COMMIT` and `SOURCE_COMMIT` are both accepted as build args, and whichever
one your platform injects ends up as the version label in the web UI. It is the
cheapest way to answer "is this deploy actually live".

### Health gating

The image's `HEALTHCHECK` sets a **10-second start period**, which is what makes
a deploy report healthy at around ten seconds rather than around thirty.

Without a start period there is a window where a working container is still
marked unhealthy and the platform answers 502. Worth knowing before you go
looking for the fault in the application.

## DNS and TLS

One hostname is enough. The API, the MCP endpoint, the UI and these docs all
come out of one container on one origin, so there is nothing to split across
subdomains.

Proxying the record rather than pointing it at the origin directly keeps the
origin IP private and terminates TLS at the edge. That is a preference, not a
requirement — a certificate on the origin works too.

### Retiring a hostname

If you ever split the API onto its own subdomain and later merge it back, the
old name needs retiring properly, and that is worth doing deliberately.

<Callout type="warn">
A client configuration is not something you can migrate on someone's behalf.
Every client pointed at the old hostname has to be repointed by hand, so a
retirement is a thing to announce, not just to do.
</Callout>

<Callout>
While a proxied DNS record outlives its origin, the hostname does not fail
cleanly. It answers the proxy's own error — Cloudflare's is
**`no available server`** — which is a 503 from the edge with nothing behind it.

That reads like a database or application problem and is neither: it means a
route with nothing attached. **Deleting the DNS record is the tidy end of a
retirement.** Until it goes, the name keeps resolving and keeps answering 503,
which is a slower and more confusing way to say "this host is gone" than a clean
NXDOMAIN.
</Callout>

## Database

Any reachable Postgres, managed or self-hosted. [Database](/run/database) covers
the trade-offs, what pgvector buys you, and what happens without it.

The one deployment-shaped detail: the container runs `alembic upgrade head`
before it binds a port, so a failed migration stops the deploy rather than
leaving a half-migrated database serving traffic. A platform that health-checks
aggressively during that window will see the container as down. It is not.

## Keeping a record

Whatever you choose, write it down somewhere versioned, and update it in the
same change that moves it.

The failure mode is specific and common: six months later nobody can say where
the DNS record points or which port the proxy targets, and the only way to find
out is to log into three dashboards.
