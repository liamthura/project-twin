## The shape of it

```text
Cloudflare  (DNS + proxy, TLS terminates here)
      ↓
Coolify on a VPS  (builds and runs the container)
      ↓
one container  →  /   /api   /mcp   /docs
      ↓
Postgres + pgvector  (same host)
```

## Cloudflare

**One hostname: `mygist.thuradev.qzz.io`.** It is proxied through Cloudflare
rather than pointing at the origin directly, so the origin IP stays private and
TLS terminates at the edge.

### `mygist-api.thuradev.qzz.io` is retired

The API and MCP endpoint once had their own hostname, separate from the UI. The
single-container merge made that unnecessary, and it has now been retired
outright.

<Callout type="warn">
**Anything still configured against `mygist-api` is broken, not degraded.** A
client config is not something you can migrate on someone else's behalf, so the
only fix is for each client to be repointed at `mygist.thuradev.qzz.io/mcp` by
hand.

If you are the one who retired it, that is a decision to communicate, not just
to make.
</Callout>

<Callout>
While the DNS record survives its origin, the hostname returns Cloudflare's
**`no available server`** rather than a DNS failure — a 503 from the edge, with
nothing behind it.

That reads like a database or application problem and is neither. It means a
route with nothing attached. **Removing the DNS record is the tidy end of a
retirement**: until it goes, the name keeps resolving and keeps answering 503,
which is a slower and more confusing way to tell someone the host is gone than a
clean NXDOMAIN.
</Callout>

## Coolify

Deploys trigger on pushes to `main`.

| Setting | Value |
|---|---|
| Build context | The **repository root** |
| Dockerfile | `./Dockerfile` |
| Container port | **1120** |
| Trigger | Push to `main` |

<Callout type="warn">
**The container port is 1120, not 8000.** It was 8000 until it was moved off the
generic default.

Nothing in the repository can enforce this end of it: the platform's own port
mapping lives in a dashboard. If a deploy goes out and the proxy still points at
8000, every request 502s while the container itself is perfectly healthy.
</Callout>

The context is the repository root because the image builds the frontend and
the documentation before assembling the Python image.

`SOURCE_COMMIT` is injected at build time and ends up as the version label in
the web UI — which is how you tell what is actually deployed.

### Health gating

The image's `HEALTHCHECK` has a **10-second start period**, and that is what
makes a deploy report healthy at around 10 seconds rather than around 31.

Without it there is a window where a perfectly working container is still marked
unhealthy and the platform answers 502. Worth remembering before blaming the
application for a flaky deploy.

## Database

Self-hosted Postgres with pgvector, on the same VPS.

Not a managed provider. Older documentation describing Neon as the production
database is out of date — though Neon remains a fine option for anyone else.

## Keeping this page true

If you move any of this, update this page in the same change.

The failure mode is not that something breaks. It is that six months later
nobody can say where the DNS record points, and the only way to find out is to
log into three dashboards.
