Organised by what you are seeing, not by what is wrong.

## The server will not start

<Accordions>

<Accordion title="core section pack(s) failed to load">

A manifest in `backend/section_packs/` is invalid, and the message names it.

Packs shipped in the repository raise rather than being skipped, so this is the
loader doing its job. Fix the manifest; the error names the offending key.

See [Section packs](/run/section-packs#an-invalid-pack-stops-the-server).

</Accordion>

<Accordion title="PackError: section pack <name>: invalid manifest">

The same thing, reported for a pack the server does not own.

Before this behaviour existed, such a pack disappeared silently and the symptom
surfaced much later as an unknown entity type.

</Accordion>

<Accordion title="A migration failed and the container never bound a port">

Working as designed. The container runs `alembic upgrade head` before binding,
so a failed migration stops the deploy instead of leaving a half-migrated
database serving traffic.

Read the Alembic error. The application never started, so nothing after that
point is relevant.

</Accordion>

<Accordion title="Cannot connect to the database">

Check `DATABASE_URL` reaches the host from *inside* the container, not from your
laptop. `localhost` in a container is the container.

</Accordion>

</Accordions>

## A client cannot see the tools

Work outwards from the server. Each check rules out one layer.

```bash
# 1. is the server up? (public, no token)
curl -s https://your-instance/api/health

# 2. does the token work?
curl -s https://your-instance/api/auth/whoami \
  -H "Authorization: Bearer YOUR_TOKEN"
```

| Symptom | Means |
|---|---|
| Connection refused, or a DNS failure | The server or the network, not your config |
| `no available server`, or another proxy-level 503 | A proxied hostname with nothing behind it. A routing problem, **not** a database one, and usually a client still pointed at a hostname that has been retired. See [Infrastructure](/run/infrastructure#retiring-a-hostname). |
| `401` on whoami | The token is wrong, revoked, or not being sent. Check the client is passing `Authorization` and not stripping it. |
| Both checks pass, client still blank | The client's configuration, covered in [Other clients](/use/clients) |

<Callout type="warn">
If you put a reverse proxy in front, check it is not rewriting `/mcp` or adding
a trailing slash. The endpoint is mounted at the root of the app so it resolves
exactly, and a redirect breaks clients that do not follow redirects on POST.
</Callout>

## Sign-in and OAuth

Nearly every failure here arrives as a bare `401` or an OAuth error code that
names neither the setting nor the fix, so match on the symptom rather than on
the message.

Read the API's startup log first. Where OAuth is configured, the API checks
its own `AUTH_ISSUER` against what the auth service advertises and says so:

```text
INFO   auth issuer agreed with the auth service: https://your-instance/auth
```

Anything other than that line is the answer to most of what follows, without
reproducing anything.

<Accordions>

<Accordion title="Sign-in works, then every page 401s on /api">

`AUTH_ISSUER` on the API does not match the `iss` claim the auth service signs.
It is the public origin **plus `/auth`**: `https://your-instance/auth`, not
`https://your-instance`.

The startup log says so directly, with both values:

```text
ERROR  auth issuer mismatch: OAuth cannot work.
           AUTH_ISSUER = https://your-instance
           advertised  = https://your-instance/auth
```

See [The `/auth` suffix](/run/self-hosting#the-auth-suffix). Recreate the
container after changing it; a restart reuses the old environment.

</Accordion>

<Accordion title="Clients discover an authorization server that then registers nothing">

`AUTH_MCP_RESOURCE` is set on the API and not on the auth service, so discovery
resolves and `/auth/oauth2/register` does not exist. Connecting fails after the
browser has already opened, which is the most confusing point at which it can.

The startup log names this one too:

```text
ERROR  the auth service has no OAuth endpoints, but this API expects them
```

Set the same value on both containers and recreate them.

</Accordion>

<Accordion title="VALIDATION_ERROR: Redirect URI must use HTTPS (HTTP allowed only for loopback hosts)">

The client's registration was refused, before any browser opened. Nothing is
wrong with the instance: the redirect URI the client asked to register is one
the standard does not permit.

| Redirect URI | |
|---|---|
| `https://anything/callback` | accepted |
| `http://127.0.0.1:9876/callback` | accepted |
| `http://localhost:9876/callback` | accepted |
| `myapp://oauth/callback` — a private-use scheme | accepted |
| `http://0.0.0.0:9876/callback` | **refused** |
| `http://192.168.1.50:9876/callback` | **refused** |
| `http://app.example.com/callback` | **refused** |

The rule is RFC 8252 §7.3 and the OAuth 2.1 security BCP: a native app
redirects to a loopback address or to a private-use scheme, and plain `http` to
any other host is refused because the authorization code would cross the
network in clear text. It is enforced by Better Auth and is not configurable
here, which is the correct outcome for a server holding personal data.

## The usual cause: the client's own dashboard is not on loopback

Nearly always this is a client with a web UI that you reach at something other
than `localhost` — over a tunnel, a VPN such as Tailscale, or a reverse proxy.
Such a client builds its OAuth callback from **the origin you opened it at**, so
opening it at `http://your-host:9119` produces
`http://your-host:9119/…/callback`, and that can never register.

The same client used entirely on one machine works, which is what makes this
confusing: nothing about the client changed, only the address you reached it at.

### Fixes, best first

**Give the client's dashboard an HTTPS origin.** The callback follows it, and
this fixes every strict provider at once rather than this one. On a tailnet,
`tailscale serve` issues a real certificate for exactly this case; behind a
reverse proxy, terminate TLS and point the client's public-URL setting at the
HTTPS name.

**Or pin the callback to loopback.** Where a client lets you set the redirect
URI explicitly, `http://127.0.0.1:<port>/callback` is always accepted, even when
the dashboard itself is reached remotely. Contained, but it only fixes this one
server.

<Callout type="warn">
If a client picks a **new random callback port** on a later attempt while
reusing a cached `client_id`, registration succeeds and the authorization then
fails on a redirect-URI mismatch. Clear the client's stored credentials for this
server and let it register again.
</Callout>

<Callout>
`0.0.0.0` is refused for the same reason, and is worth knowing separately: it is
an *unspecified* address, not a loopback one. A client that binds `0.0.0.0` and
reuses that string in its callback is refused where `127.0.0.1` is accepted.
</Callout>

A refused registration stores nothing, so there is no partial state to clean up
and retrying costs nothing once the URI changes.

The refusal names the offending URI and the accepted shapes in its `message`,
with the list repeated in `rejected_redirect_uris` — so the response itself
should tell you which of your URIs was the problem.

</Accordion>

<Accordion title="A client finishes consent, then reports its credentials were rejected">

The same defect, seen from the other end: the access token reached `/mcp` and
failed verification there. Check `AUTH_ISSUER` first, then `AUTH_MCP_RESOURCE`.

An access token's `aud` claim must equal `AUTH_MCP_RESOURCE` exactly, and both
containers have to carry the identical string: no trailing slash on one and
not the other.

<Callout type="warn">
If correcting `AUTH_ISSUER` for one of these two symptoms produces the other,
you are on a build from before the two token types were reconciled. No value
satisfies both on those builds. Upgrade.
</Callout>

</Accordion>

<Accordion title="The client never offers to sign in, or discovery 404s">

```bash
curl -s https://your-instance/.well-known/oauth-protected-resource
```

A 404 means `AUTH_MCP_RESOURCE` is unset, which gates the entire OAuth surface:
no discovery documents on the API, no OAuth endpoints on the auth service.
That is the intended state for an instance that has not opted in; clients use
[bearer tokens](/use/clients#connecting-with-a-token) instead.

Set on the API only, clients discover an authorization server that serves
nothing. Set it on both containers or on neither.

</Accordion>

<Accordion title="invalid_scope: offline_access while connecting">

Fixed. A client registered itself from the advertised scope list, which omits
`offline_access` deliberately, and was then refused the refresh token it needs.
If you see it, you are on an older build.

</Accordion>

<Accordion title="The consent screen never leaves the consent screen">

Fixed, on both **Allow** and **Deny**. The screen read the wrong key off the
server's response and so never learned where to send the browser back to. If
you see it, you are on an older build.

A 500 naming `invalid input syntax for type timestamp with time zone` at the
same point in the flow is a second fixed bug with the same cause of confusion:
token lifetimes are counts of seconds, and a time-span string produced a
`NaN` expiry.

</Accordion>

<Accordion title="Sign-up is open when it should be closed, or closed when it should be open">

`INVITE_ONLY` is read by **both** containers, and only the literal string
`true` turns it on. `1`, `yes` and `on` are read as off, so the gate fails open,
quietly.

Set on only one container it is a gate on one of two doors: the auth service
owns Better Auth's sign-up, and the API owns the deprecated
`/api/auth/register` that detached mode still uses.

`/api/instance` reports which mode the API believes it is in.

</Accordion>

</Accordions>

## Search behaves oddly

<Accordions>

<Accordion title="Paraphrases miss, exact words hit">

You are in FTS-only mode. Either pgvector is absent, or no embedding provider is
configured. Check the startup log.

See [Database](/run/database#pgvector).

</Accordion>

<Accordion title="persona_search.embedding is vector(N) but EMBEDDING_DIM=M">

The column and the configured width disagree, so the server fell back to
FTS-only rather than writing vectors it could never compare.

Run the backfill with `--recreate`, **then restart the server**. The running
process cached the decision at startup and will not re-check until it reboots.

</Accordion>

<Accordion title="days returns nothing, and everything looks edited today">

Expected right after a `--recreate` backfill, which resets every entry's
last-change time. It settles as entries change.

See [Search index](/run/search-index).

</Accordion>

<Accordion title="Nothing is indexed at all">

An imported persona lands in `persona_data` but not in `persona_search`.
Backfill it.

</Accordion>

</Accordions>

## Data looks wrong

<Accordions>

<Accordion title="The raw JSON doesn't match what the editor shows">

Almost always read-time normalisation. `persona_store` coerces a handful of
shapes as data is read: every coercion is lossless and idempotent, and the
editor shows the normalised form.

This is not corruption, and there is nothing to do about it.

</Accordion>

<Accordion title="An entry has no id">

Some nested lists, such as a project's references or a hobby's specifics, have
no ids by
design, and are addressed through their parent instead.

Rows written before an id backfill also lack them until the next time they are
saved.

</Accordion>

<Accordion title="A field an AI client sent was not saved">

Check `get_schema` for that entity. The field is probably not in the vocabulary,
and a rejection is the correct outcome.

Historically the most common cause was different: a field that was *documented*
but never stored. The stored-key audit now makes that impossible to introduce; see
[Section packs](/run/section-packs#guards).

</Accordion>

<Accordion title="Two clients disagree about what is stored">

They cannot. There is one copy, with no caching between clients.

Check they are authenticating as the same account: two tokens can belong to two
different users on the same server.

</Accordion>

</Accordions>

## Deploys

<Accordions>

<Accordion title="The container serves an old build after a restart">

`docker restart` reuses the existing container and its image layer. Recreate it
instead:

```bash
docker rm -f mygist && docker run … mygist
```

A quick way to confirm which build is actually being served is to compare the
hashed asset filename in the served HTML against the one the build produced.

</Accordion>

<Accordion title="A stream of 502s just after deploying">

Health gating. The image's `HEALTHCHECK` has a 10-second start period; if your
platform routes on health, there is a window where a working container is still
marked unhealthy.

See [Infrastructure](/run/infrastructure#health-gating).

</Accordion>

<Accordion title="/docs 404s but /docs/ works">

Fixed: the bare path now redirects. If you see it, you are on an older build.

</Accordion>

</Accordions>

## Getting more detail

`get_raw` dumps a section file verbatim, bypassing every read scope. It is the
fastest way to see what is *actually* stored, rather than what a scope chose to
show.

For the REST side, `/api/docs` is a live Swagger UI against the running
instance.
