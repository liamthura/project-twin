title: Search index
description: How the index is maintained, and the restart step that is easy to miss.
---

`persona_search` holds one row per entity: a full-text vector, and — where
embeddings are configured — an `embedding` column.

It is **derived** from `persona_data`, so it can always be rebuilt. Nothing is
lost by dropping it.

Entities are indexed automatically as they are written. You only need the
backfill script for entries that already existed when something changed.

## When to backfill

- You configured an embedding provider for the first time.
- You changed `EMBEDDING_MODEL` or `EMBEDDING_DIM`.
- You imported a persona from JSON.
- The index looks wrong and you want it rebuilt.

## Running it

From `backend/`:

```bash
# index anything missing or changed
python scripts/backfill_search_index.py

# drop and recreate the embedding column at EMBEDDING_DIM, then re-embed
python scripts/backfill_search_index.py --recreate
```

It reads `DATABASE_URL` and the `EMBEDDING_*` variables exactly as the server
does, including from `.env`.

Use `--recreate` whenever `EMBEDDING_DIM` changes. The existing column is at the
old width and cannot simply be written into.

## The two gotchas

Both of these have cost real debugging time. They are here so they cost you
none.

<Callout type="warn">
### `--recreate` is not enough on its own. Restart the server too.

If the server booted and logged:

```text
persona_search.embedding is vector(N) but EMBEDDING_DIM=M
```

then it cached the decision at startup and is running FTS-only. Fixing the
column does **not** change that — the running process only re-checks when it
restarts.

Backfill, then restart. Otherwise you will spend an afternoon debugging a
perfectly correct index that nothing is using.
</Callout>

<Callout>
### `--recreate` resets every entry's last-change time.

Three things read that timestamp, and all three go quiet afterwards until
entries start changing again:

- `search_context(days=…)` returns nothing for a window that should have hits.
- `updated_at` on `get_entity` and on titles-mode reads shows today for
  everything.
- The top-of-mind staleness advisory is suppressed for 30 days.

Nothing is lost — these timestamps describe indexing, not your data. But a
persona that looks suspiciously "all edited today" right after a recreate is
expected, not a bug.
</Callout>

## Verifying it worked

The quickest check is a search that should obviously hit:

```text
search_context("something you know is in there")
```

Then test the difference between the two modes. Search for a **paraphrase** of
something stored, using none of its actual words:

- **Paraphrase hits** — you are in hybrid mode. Embeddings are working.
- **Paraphrase misses, exact word hits** — you are in FTS-only mode. Check the
  provider variables and the startup log.

## Cost and privacy

Embedding calls happen on write and during backfill, not on read. A backfill of
a large persona is therefore a one-off burst of API calls rather than an ongoing
cost.

If you would rather no persona text left the server, either run FTS-only or
point `EMBEDDING_API_URL` at a local embedding server. See
[Database](/run/database#pgvector).
