A **section pack** adds a whole persona section from a single file:

```text
backend/section_packs/<key>/manifest.json
```

No Python. No React. One JSON file, and you get all of this:

| You get | Without writing |
|---|---|
| A place to store the data | Any storage code |
| MCP tools that write into it | Any tool handlers |
| A full editor UI | Any React |
| Search indexing over the entries | Any indexing code |
| Stable ids on every entry | Any id logic |
| A read scope of its own | Any scope assembly |
| A toggle in the Sections manager | Any settings plumbing |

Packs are declarative *only*. A pack cannot ship code, which is what makes
accepting one from a stranger a reasonable thing to do.

<Callout>
This page is the walkthrough. [Manifest reference](/run/pack-reference) is the
exhaustive list of every key. `docs/CONTRIBUTING-PACKS.md` in the repository is
the authoring guide, and `backend/section_packs/meta_schema.json` is the
authority above all three.
</Callout>

## The one rule

A node's `kind` states the shape of the value at its `path`.

That is the format. A node at `path: ["education"]` with `kind: "list"` says the
stored file holds `"education": [ {...}, {...} ]`. `kind: "fields"` says the value
there is one object with named keys. `kind: "strings"` says it is an array of
bare strings, with nothing inside to name. A `group` binds no value at all, so it
takes no `path`.

A `list` or `fields` node then carries an `element`, which describes one member
of what the node binds: one row of the list, or the one object the `fields` node
is. Everything else follows from those two sentences.

## Before you start

Ask whether you need a new section. A new **field on an existing entity** is a
smaller change with a smaller cost, and most ideas are that.

A new section earns its place when the data is a genuinely separate area of a
person's life, one that some users will want and others will not. That is why
sections can be toggled, and why new ones default to off.

## A worked example

We will build a **Tools** pack: the software and hardware someone works in.
Useful context, since an assistant that knows you live in Neovim and zsh gives
different answers, and it exercises most of what a pack can do.

<Steps>

<Step>

### Copy the template

```bash
cp -r backend/section_packs/_template backend/section_packs/tools
```

The directory name is the section key: lowercase, `snake_case`. The manifest's
`"key"` must match it exactly.

</Step>

<Step>

### Identify the section

```json title="backend/section_packs/tools/manifest.json"
{
  "$schema": "../meta_schema.json",
  "key": "tools",
  "title": "Tools",
  "description": "Software and hardware you work in day to day",
  "core": false,
  "default_enabled": false,
  "position": 45
}
```

| Key | What it does |
|---|---|
| `title`, `description` | Shown in the Sections manager and on the section's card |
| `core` | `true` means it can never be disabled. Only three shipped sections are core. **Yours is not.** |
| `default_enabled` | `false` for anything new. Users opt in. |
| `position` | Where it sits in the editor's tab order. Pick a gap between existing packs. |

<Callout>
`$schema` points at `meta_schema.json`, so an editor with JSON schema support
autocompletes and validates the whole file as you type. Every object in a manifest
is closed, so a mistyped key fails at boot rather than being ignored. Catching it
in the editor is quicker.
</Callout>

</Step>

<Step>

### Declare the storage shape

`defaults` is the empty skeleton a brand-new account starts with.

```json
"defaults": {
  "items": []
},
"id_lists": [
  ["items", "tool"]
]
```

`id_lists` pairs a stored array with an id prefix. Every entry in `items` gets an
id like `tool_a1b2c3`, which is what makes it addressable by `get_entity` and
linkable by [relations](/use/relations).

<Callout type="warn">
Every path named in `id_lists` must exist in `defaults` **as a list** and be
bound by a top-level `list` node, and the prefix must be unique across every pack
in the repository. All three are checked at boot.
</Callout>

</Step>

<Step>

### Draw the section

`sections` is a list of nodes. One `list` node is enough to start, and it is both
the editor and the write vocabulary:

```json
"sections": [
  {
    "kind": "list",
    "path": ["items"],
    "element": {
      "entity": "tool",
      "identifier": "name",
      "fields": [
        { "name": "name", "role": "title", "required": true },
        { "name": "kind", "type": "enum", "show": ["form", "badge"],
          "values": ["editor", "language", "shell", "database", "hardware", "service"] },
        { "name": "role", "type": "enum", "show": ["form", "badge"], "default": "daily",
          "values": ["daily", "occasional", "learning", "retired"] },
        { "name": "notes", "type": "longtext" },
        { "name": "tags", "type": "strings" }
      ]
    }
  }
]
```

The stored value at `items` is an array of objects, so `kind` is `list` and
`element` describes one tool. That gives you a list of expandable rows: `name` is
the row title, `kind` and `role` draw as chips on the collapsed row and as
controls in the expanded one, and expanding a row shows a `notes` textarea and a
tag input.

Each field is declared once. `name` is the stored key, and everything else about
the field sits beside it:

| Key | What it does here |
|---|---|
| `role: "title"` | Names a row. Exactly one field per row carries it. |
| `required: true` | An `add` must carry it. Derives the entity's `required`. |
| `type` | `text` unless you say otherwise. `longtext` gets a textarea, `strings` a tag input. |
| `values` | The vocabulary of an `enum`, and the options its control offers. |
| `default` | Prefilled in the form, and applied on an MCP `add`. |
| `show` | Where the field draws. `["form"]` if you say nothing. |

`identifier` is the field an MCP client names a row by for `update` and `remove`.
It has to name a declared field, and that field should be `required`, because a
row whose identifier may be absent cannot be updated or removed by anyone.

<Callout type="warn">
Nothing catches a misspelled field name. It becomes a new field in the contract
and a control writing a key nothing reads, because the manifest is the authority
on what the stored keys are. Read your derived contract before opening a PR, with
the command two steps down.
</Callout>

</Step>

<Step>

### Say what each scope pulls

```json
"scope_contributions": {
  "professional": ["items"]
}
```

A client asking for the `professional` scope now gets your tools. Omit a scope to
stay out of it.

Your section always gets **its own scope token for free**. `get_context(scope:
"tools")` works whether or not it contributes to any global scope, so
contributing to nothing is a legitimate choice for something niche.

<Callout>
Be conservative. Everything you add to a global scope costs tokens in every
conversation of every user who has your pack enabled. `professional` alone is the
right answer here; adding it to `minimal` would not be.
</Callout>

</Step>

<Step>

### Boot it

```bash
cd backend && python main.py
```

An invalid manifest raises a `PackError` naming your pack and the offending key.
Fix, repeat. The error message is the development loop.

Once it boots, the section is live: it appears in the Sections manager, `tool`
appears in `get_schema`, and the editor draws it.

</Step>

<Step>

### Read what it derived

```bash
cd backend && python3 -c "
import json, pack_loader
print(json.dumps(pack_loader.derive_entities(json.loads(
    open('section_packs/tools/manifest.json').read())), indent=2))
"
```

Every name in that output is a name you wrote. Check each one before a client
ever sees it.

</Step>

<Step>

### Test it

```bash
cd backend
python -m pytest tests/test_pack_loader.py -q   # the loader and the schema
python -m pytest -q                             # the mechanical guards
```

The full suite is where the [guards](#guards) live. Run it before
opening a PR, because they check things the loader does not.

</Step>

</Steps>

## The contract you did not write

There is no `entities` block. `pack_loader.derive_entities` computes the contract
MCP clients see from the field descriptors, and `get_schema` ships the result.
The five descriptors from step four derive this:

```json
{
  "tool": {
    "actions": ["add", "update", "remove"],
    "required": ["name"],
    "optional": ["kind", "role", "notes", "tags"],
    "identifier": "name",
    "valid_values": {
      "kind": ["editor", "language", "shell", "database", "hardware", "service"],
      "role": ["daily", "occasional", "learning", "retired"]
    },
    "field_defaults": { "role": "daily" }
  }
}
```

`required` and `optional` come from the descriptors, `identifier` from
`element.identifier`, `valid_values` from the two enums, `field_defaults` from
`role`'s `default`, and `actions` from the default for a list. Rename a field and
the contract follows, which is the point. [Manifest
reference](/run/pack-reference#the-derived-contract) has the whole mapping.

Older manifests declared all of that by hand, beside a UI node that named the same
fields again, and they also listed phrases that hinted a message might belong to
the section. All of it is gone. The phrase matcher gave way to
[proposals](/use/capture), so there is nothing to declare for capture either: your
section is reachable the moment its entities exist.

## What you just got

Without writing a line of code, an AI client can now do this:

```text
get_schema(entity="tool")
  → actions, required and optional fields, valid values, a worked example per action

persona_modify(
  action="add", entity="tool",
  data={"name": "Neovim", "kind": "editor", "role": "daily"}
)
  → stored as items[0], with id tool_a1b2c3

get_context(scope="tools")
  → your tools

search_context("neovim")
  → the entry, ranked, with its id
```

And the same data is fully editable in the browser.

## Making it nicer

The minimal version works. These options are what separate it from the shipped
packs, and each is a key on the field or the node it belongs to.

### Help people fill it in

```json
{ "name": "name", "role": "title", "required": true,
  "placeholder": "e.g. Neovim, Postgres, Framework 13",
  "suggestions": ["VS Code", "Neovim", "zsh", "Docker", "Postgres"] }
```

`placeholder` sets the greyed-out example text. `suggestions` renders tap-to-add
chips in the Add dialog, which is the single biggest thing you can do for a
section nobody knows how to start filling. Only the title field's suggestions are
read, since a suggestion is a proposed row rather than a proposed value for some
other key.

### Make a long list usable

```json
"search": true,
"facets": ["kind", "role"],
"sort": { "field": "name", "dir": "asc" }
```

Three keys on the `list` node. `search` adds a filter box, `facets` turns enum
fields into filter chips above the list, and `sort` orders the rows for display
without ever reordering the stored array. `facets` entries must name `enum`
fields, because the chips are built from the vocabulary.

### Explain the section

A node's `description` is one muted line under its title. `info` is
`{overview, tips[]}`, the content of the section's info dialog, for anything
longer. The complete manifest above carries one on the list node.

### Show more on the collapsed row

`show` is an array, because a field can hold several positions at once. The five
are `form` (the default control), `badge` (an editable chip on the collapsed
row), `row` (the faded secondary line), `count` (an "N tags" chip for an
array-valued field) and `pin`, each described in the
[reference](/run/pack-reference#show).

`kind` and `role` above say `["form", "badge"]`, so they are chips on the
collapsed row and controls in the expanded one. Order within a position comes
from the order of the `fields` array, so one list of descriptors fixes the form
order and the badge order together.

For a value the server writes and the user must not edit, add `ui_only: true`
alongside a read-only position. `show: []` means stored and drawn nowhere, and
the loader rejects it unless the field is `ui_only` or a labelled array.

### Longer text fields

```json
{ "name": "notes", "type": "longtext" }
```

A field that wants a textarea says so. There used to be a name heuristic, where a
field called `notes`, `why` or `description` became a textarea whether the
manifest said so or not, and it is gone. A `notes` field that omits the type gets
a one-line input, silently and correctly.

## Nested arrays

A nested array is a field with `type: "list"` and an `element` of its own. There
is no separate child-node concept: a `list` field's `element` and a `list` node's
`element` mean the same thing, and as a field inside a row's `fields` the only
possible reading is that it binds against the row.

```json
{
  "name": "configs", "type": "list", "label": "Configs", "show": ["count"],
  "element": {
    "entity": "tool_config",
    "identifier": "name",
    "actions": ["add", "remove"],
    "description": "A dotfile or setting worth remembering, on one tool.",
    "parent": "tool_name",
    "fields": [
      { "name": "name", "role": "title", "required": true, "placeholder": "e.g. init.lua" },
      { "name": "url", "placeholder": "https://github.com/you/dotfiles" },
      { "name": "notes", "type": "longtext" }
    ]
  }
}
```

A `strings` or `list` field with a `label` draws its own titled section under the
row, with its own add and remove, and that is what makes it a block. Without a
label it is an inline control in the detail grid. A block may not also claim the
`form` position, since the block is the field's control, and the loader rejects
that pair rather than letting the renderer discard the position. `show: ["count"]`
is about the parent row, and is independent of the block.

`parent` is the MCP parameter a client passes to say which row it means. It must
name the enclosing element: its `identifier` bare, or that identifier prefixed by
the enclosing entity's name. Here `tool`'s identifier is `name`, so `tool_name` is
legal and so is `name`.

<Callout type="warn">
Get `parent` wrong and the manifest is still internally consistent, which is how
profile once shipped Education and Work Experience with their nested entities
swapped. Each block's entity and parent agreed with each other and only disagreed
with the row they sat under, so nothing noticed. The loader now checks the pair
against the enclosing element.
</Callout>

That field derives a second entity, which writes into an array belonging to a
parent row:

```json
{
  "tool_config": {
    "actions": ["add", "remove"],
    "required": ["tool_name", "name"],
    "optional": ["url", "notes"],
    "identifier": "name",
    "parent": "tool_name",
    "description": "A dotfile or setting worth remembering, on one tool."
  }
}
```

<Callout>
Nested entries have **no ids of their own**. They are addressed through their
parent, which is why a project's references cannot be linked to directly.
</Callout>

For a nested array of bare strings, use `type: "strings"` and give its `element`
an `entity` and an `identifier`, which is the parameter name for one string.
Profile's work `highlights` and `skills` both work that way. Leave the `element`
out and the array is editable in the app and invisible to MCP, which is what most
string arrays want.

## Not everything is a list

Four node kinds exist, and what each one binds is the difference between them.

| `kind` | The value at `path` is | Renders |
|---|---|---|
| `list` | an array of objects | Expandable rows, badges, an Add dialog |
| `fields` | one object with named keys | A form. `path: []` addresses the section root. |
| `strings` | an array of bare strings | Chips, or one editable row per string |
| `group` | nothing, since it binds no path | A heading with nested `sections` under it |

A `group` is a visual container, and its children's `path` still resolves against
the section root. The complete manifest above ends with one: an Environment band
holding a `fields` node at `["environment"]` and a `strings` node at
`["environment", "shortcuts"]`, which is why `defaults` carries an
`"environment": {}` for them to bind into.

The `fields` node is one object, edited in place, so its `element` needs no
`identifier` and its `actions` default to `["update"]` alone. The `strings` node
has no `element`, so its array is editable in the app and no client can write it.

<Callout>
`control` on a `strings` node or field is worth getting right. The default,
`"chips"`, renders each string as a chip, which is correct for short word-like
values you add and remove but never revise. `"input"` gives each string its own
editable row, which is correct for **sentences**, where a typo in a chip means
deleting and retyping the whole thing.

Work highlights and learning-log decisions both use `"input"` for that reason.
</Callout>

## Commenting a manifest

JSON has no comment syntax, so nodes and fields accept a `$comment` key. The
loader ignores it, no renderer reads it, and it never reaches a client.

```json
"$comment": "`primary` marks the one entry that IS the user's design language, as opposed to a style they merely like. Kept to a single holder by `exclusive: true`, which both writers honour."
```

Use it. The shipped packs use it heavily, and it is the only place a non-obvious
decision can live next to the thing it explains. An `element` has no `$comment`
of its own, so there is one place per node to look.

## Guards

The test suite checks packs mechanically, and it will reject things that look
fine to a human. Each of these exists because it caught a real defect.

<Accordions>

<Accordion title="Every field the contract declares must actually be stored">

A field nothing writes fails the **stored-key audit**, for both `add` and
`update`.

The audit is empirical rather than declarative: it runs each action twice with two
different values and diffs what came out. So it needs no maintenance and sweeps
new entities automatically, including yours. Since the contract is derived from
your descriptors, every field the editor renders is a field the audit probes.

If a field is genuinely a *router* the caller must send rather than something
stored, it says `write_only: true` and carries a reason in its `$comment`.
`sleep.day_type` is the standing example: it selects whether to write the weekday
or weekend sub-object and is never itself stored.

</Accordion>

<Accordion title="An add built from exactly your required fields must succeed">

If you declare one `required: true` field but the write path demands four, the
contract and the implementation disagree, and a client has no way to find that
out except by failing.

The test builds an `add` from precisely what your descriptors derived and asserts
it works.

</Accordion>

<Accordion title="The derived contract must match the one that was frozen">

`tests/fixtures/entity_schema_v1.json` holds the 42 entities across 10 packs that
`get_schema` reported before the manifest format changed, and
`test_entity_schema_frozen.py` asserts the derivation still equals it, entity for
entity and key for key. That is the whole safety argument for computing a schema
that used to be copied by hand.

It is inert for a new pack, whose entities are not in the frozen file. On an edit
to a shipped pack it is what tells you a rename changed the MCP contract.

</Accordion>

<Accordion title="A rendered field must not bind an input-only spelling">

`execute_modify` normalises several accepted input spellings down to one stored
key. A control bound to one of the other spellings renders fine and its edits
vanish on save, silently and permanently.

`FIELD_ALIASES` in `server.py` is the only enumeration of those spellings, so
`test_section_bindings.py` checks your field names against it. It is inert for an
entity `FIELD_ALIASES` does not name, so a pass there means "no authority",
never "verified safe". Declare an accepted spelling as `alias` on the field that
stores it, rather than as a field of its own.

</Accordion>

<Accordion title="Frontend fixtures must be regenerated">

`frontend/src/__fixtures__/packs.json` is generated from the manifests, and the
frontend tests assert against it.

```bash
cd frontend && npm run fixtures
```

CI runs this and then `git diff --exit-code`, so a stale fixture fails the build
rather than passing quietly.

</Accordion>

</Accordions>

Beyond those, the loader enforces the semantic rules JSON Schema cannot state,
each raising a `PackError` that names the pack and the node it failed on.
`docs/CONTRIBUTING-PACKS.md` lists them.

## An invalid pack stops the server

<Callout type="warn">
A manifest that violates `meta_schema.json` or any of the loader's rules raises
and **halts startup**. It is not skipped with a warning.

This changed deliberately. Warn-and-skip meant a single mistyped key removed an
entire section silently: the pack vanished, and the first symptom appeared much
later and nowhere near the cause, as a client being told an entity type was
unknown. It happened twice.

Failing at boot puts the error where the mistake is. Warn-and-skip survives only
for pack directories the server does not own.
</Callout>

## Common mistakes

| Symptom | Cause |
|---|---|
| Server will not boot, `PackError` names your key | Read the message. It names the offending key. |
| `additional properties not allowed` on a node | A v1 key. `entities`, `ui`, `children`, `badges`, `detail_fields` and the other parallel arrays are all gone. |
| A field is in `get_schema` and never saved | It fails the stored-key audit. Either wire it up or remove it. |
| A field is in `get_schema` under a name you did not write | A typo in `name`. The contract is derived from it. |
| A nested array writes to the wrong row | The nested `element`'s `parent` names the wrong row |
| A textarea renders as a one-line input | It needs `type: "longtext"`. Nothing infers it from the name. |
| A labelled array is rejected | A block cannot also claim the `form` position |
| `id_lists` rejected at boot | The path is not a list in `defaults`, no top-level `list` node binds it, or the prefix is taken |
| Frontend tests fail after a manifest edit | `npm run fixtures` |

## Checklist before opening a PR

- [ ] Directory name and the manifest's `key` agree
- [ ] `default_enabled: false`, and `core` is `false`
- [ ] Every `kind` matches the shape of the value actually stored at its `path`
- [ ] Every field `name` is the key you meant, checked against the derived contract
- [ ] Every field that wants a textarea says `type: "longtext"`
- [ ] Entity names and the id prefix are unique across all packs
- [ ] Scope contributions are as small as you can justify
- [ ] `python -m pytest -q` passes in `backend/`
- [ ] `npm run fixtures` produces no diff in `frontend/`
- [ ] Non-obvious decisions carry a `$comment`
- [ ] Exactly one new directory under `backend/section_packs/`

## Keep entries small

Every field you add costs context tokens for every user who enables the pack.

MyGist is a context provider. It describes a person; it does not manage their
tasks. If a field would be stale next month, it probably does not belong.
