title: Section packs

A **section pack** adds a whole persona section — storage, write vocabulary,
read scopes, search indexing and editor UI — from a single
`backend/section_packs/<key>/manifest.json`. There is no per-pack Python and no
per-pack React.

The full walkthrough lives in
[`docs/CONTRIBUTING-PACKS.md`](https://github.com/liamthura/project-twin/blob/main/docs/CONTRIBUTING-PACKS.md)
in the repository. This page covers what you need to know before you start.

## What a manifest declares

| Key | Purpose |
|---|---|
| `defaults` | The empty skeleton for the section |
| `id_lists` | `[list_field, id_prefix]` pairs; prefixes must be unique across all packs |
| `entities` | The write vocabulary — actions, required/optional fields, enum values, the `identifier` used for update and remove |
| `scope_contributions` | What each global scope pulls from this section |
| `capture_triggers` | Phrases that hint `suggest_persona_update` |
| `ui` | How the editor renders the section |
| `default_enabled` | Whether it starts on, or is opt-in |

Entity names must be unique across every pack, so a new pack cannot shadow an
existing entity.

## An invalid pack stops the server

<Callout type="warn">
A manifest that violates `meta_schema.json` raises and **halts startup**. It is
not skipped with a warning.

This changed deliberately. Warn-and-skip meant a mistyped key removed an entire
section silently: the pack vanished, and the first symptom appeared much later
and far from the cause — a client being told an entity type was unknown. Twice.
Failing at boot puts the error where the mistake is.

Warn-and-skip survives only for pack directories the server does not own.
</Callout>

So the development loop is: edit the manifest, start the server, read the error,
repeat until it boots.

```bash
cd backend && python main.py
python -m pytest tests/test_pack_loader.py -q
```

## The `ui` block

`ui.sections` is a list of nodes. The shared renderer kit
(`frontend/src/renderers/`) implements four kinds:

| Kind | Renders |
|---|---|
| `list` | A list of objects — expandable rows with fields, badges and an Add dialog |
| `fields` | Named scalar fields of one object |
| `strings` | A bare `string[]` — either tag chips or one editable row per item |
| `group` | A heading with nested nodes under it; binds no storage of its own |

A `list` node can carry `children`, which render against each row — that is how a
project's references and an education entry's coursework are edited.

## Guards you will meet

The test suite checks packs mechanically, and it will reject things that look
fine:

- **Every field an entity declares must actually be stored.** A field nothing
  writes fails the stored-key audit, for both `add` and `update`. If a field is
  genuinely a router the caller must send, it gets declared as such with a
  reason rather than quietly allowed.
- **`required` must be enough.** An `add` built from exactly the fields you
  declare required has to succeed.
- **Every stored key the fixture holds must be bound by the UI or explicitly
  excluded with a written reason.** An unbound key is unreachable in the editor
  and therefore unsaveable.

These exist because each one has caught a real defect. They are strict on
purpose, and the reason strings they demand are the documentation.
